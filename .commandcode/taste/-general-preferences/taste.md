# Taste — Evently / general preferences
- Prefers implementation-first: analyze the existing project and then implement directly, without a theoretical explanation beforehand. Confidence: 0.8
- When a complete deliverable is requested, wants it finished in one pass — do not pause to ask whether to continue between files. Confidence: 0.7
- Insists on genuinely real, end-to-end functionality: no mock data for core features, the frontend must actually call the backend, and data must persist in a real database. Confidence: 0.85
- Values honest reporting: explicitly asks not to claim something works unless it has actually been verified. Confidence: 0.85
- Never hardcodes secrets or API keys; requires them through environment variables and keeps them out of version control. Confidence: 0.8
- Wants a thorough README covering description, architecture, setup, environment variables, data model, endpoints, roles, and test credentials. Confidence: 0.7
- Communicates UI/design intent by attaching a visual reference — a screenshot, a mockup, an inline text/ASCII sketch of the desired layout (e.g., dashboard cards drawn as boxes), or the full CSS/component code of a ready-made snippet (e.g., a Uiverse.io card) — and expects that layout, structure, and effects replicated but re-themed to the app's own identity (Evently's purple `brand-*` palette) rather than copied verbatim in its original colors. Confidence: 0.8
- Pastes ready-made animated effects/components even when the snippet was written for another framework (e.g., a Next.js `'use client'` component such as the `DotField` hero background or the `GooeyNav` navbar effect) and expects it adapted to the project's actual stack (React + Vite, local CSS import) and wired into the existing components so the effect just works in the app. Confidence: 0.7
- Readily adopts third-party, drop-in CSS designs and wants them wired in wholesale (their gradients, radii, shadows, and hover/active scale effects kept), applied consistently across every sibling screen in that flow (e.g., both login and register), while leaving existing logic, validation, and helper content (like test credentials) untouched. Confidence: 0.7
- Prefers a clean, professional, modern UI and explicitly avoids gratuitous gradients, animations, and shadows, as well as screens with large empty spaces — though this is overridden when it deliberately chooses a flashier reference design (e.g., an animated, gradient-button auth card), in which case it wants those effects kept. Confidence: 0.7
- Avoids `any` in TypeScript; wants explicit, named types for the domain models (User, Event, Category, Registration, Favorite, AuthResponse, etc.). Confidence: 0.75
- Centralizes HTTP/API calls in a dedicated services layer instead of scattering `fetch` across components. Confidence: 0.75
- Wants role-aware UI: do not render nav items or actions the current user is not allowed to perform. Confidence: 0.7
- Prefers a plain REST monolith and rejects heavyweight infrastructure for this kind of project — no microservices, GraphQL, WebSockets, Redis, Docker, or Kubernetes. Confidence: 0.7
- Prefers to start/run the dev servers himself; wants the environment left clean rather than servers left running by the agent. Confidence: 0.6
- Prefers extending the existing codebase in place: preserve the current architecture, stack, authentication, and roles, and do not rebuild from scratch or delete existing data unnecessarily. Confidence: 0.75
- Requires server-side validation of all input; never trusts frontend validation alone. Confidence: 0.7
- Prefers graceful degradation on partial failure: keep the created record and inform the user clearly rather than reverting (e.g., a registration remains even if the confirmation email fails). Confidence: 0.7
- Keeps sensitive data out of tokens and QR codes — a QR encodes only a safe identifier, never passwords, JWTs, or unnecessary personal data. Confidence: 0.75
- Prefers collecting only essential user data; avoids requesting unnecessary personal fields (e.g., no national ID/DNI). Confidence: 0.7
- Wants a single shared implementation for cross-cutting logic (e.g., one search service used by both the navbar and hero, one reusable component) rather than independent duplicate systems. Confidence: 0.75
- Prefers debounce on search-as-you-type inputs so a request is not fired for every keystroke. Confidence: 0.6
- Expects search to work live: matching results/suggestions should appear automatically while typing, without requiring a button press or Enter. Confidence: 0.65
- Expects lookup/autocomplete features to draw on real-world, global data rather than only on records already present in the database — the feature should work for any plausible input (e.g., any city in the world), even when no matching record exists. Confidence: 0.65
- Wants explicit, user-facing messaging when a query yields nothing (e.g., "no events exist in this location") instead of silently showing an empty list. Confidence: 0.6
- Requires the backend to derive the acting user's identity from the authenticated JWT — the client must never be allowed to dictate who created/owns a resource (e.g., creatorId is taken from the token, not the request body). Confidence: 0.8
- Expects ownership-based authorization enforced server-side: a regular user may only edit/delete their own resources, an admin may manage any, and unauthorized attempts return HTTP 403 Forbidden. Confidence: 0.7
- Welcomes proactive suggestions of additional feature ideas/roadmap: when requesting a feature, explicitly asks for "more ideas" of what else could be added, even though only the requested scope is actually implemented. Confidence: 0.6
- Prefers a minimal role model: one authenticated user role that both creates and consumes resources, plus a separate platform-admin role — avoids proliferating roles that differ only by capability, and never lets public registration self-assign admin. Confidence: 0.7
- Wants a plain login (email + password) with no role selector. Confidence: 0.6
- When deprecating/removing a concept, expects every reference removed across schema, enums, middleware, seed, controllers, services, validations, frontend, and docs — no dead/leftover code for the removed concept. Confidence: 0.7
- Reports bugs with a screenshot of the on-screen error plus a brief "can you see the error?" style request; expects the agent to investigate (read logs, reproduce) and fix the underlying root cause, not just explain or paper over it. Confidence: 0.6
- Prefers a pragmatic MVP-compatible stopgap for an optional or hard sub-feature (e.g., storing uploaded images as client-compressed data URLs in the DB when no object storage exists) rather than blocking the whole feature, and wants the chosen tradeoff documented. Confidence: 0.7
- Expects a user who owns a resource to be able to edit and delete it from every place that resource is displayed (e.g., both the item list and the detail page), not only from one of them, so a mistake is always fixable. Confidence: 0.65
- Does a dedicated visual-polish pass over the frontend after functionality works, improving sections one at a time rather than redesigning everything at once. Confidence: 0.6
- For prominent sections like the hero, prefers an open, full-width layout with a soft, diffuse background (blurred colour glow blobs in the brand purple) over a bounded, solid-colour card, with an oversized "floating" headline, a short supporting paragraph, and the primary action (search box) placed directly below. Confidence: 0.6
- Wants the brand purple used as the actual section background, not merely as accents on a white page: prominent sections should be full-bleed with a purple gradient (e.g., `bg-gradient-to-br from-brand-600 via-brand-700 to-brand-900`) and white text/content on top. Confidence: 0.65
- Wants adjacent top-of-page regions to read as one continuous block: the navbar should use exactly the same background colour as the hero, with no separating border between them, and the section directly below should carry the same hue as a soft tint so the whole area feels unified. Confidence: 0.65
- Prefers Poppins as the app's typeface (over the default Inter); wants it loaded once and set through a single global font token so the whole app (hero, navbar, buttons, inputs) uses it. Confidence: 0.7
- On coloured (e.g., purple/brand) backgrounds, prefers to eliminate plain white text/content entirely — including on input/search surfaces (navbar and hero search bars) — and keeps the replacement within the brand's own palette: light lavender (`brand-200`/`brand-300`) for text/icons and very dark purple (`#3b0764`) for buttons/active pills, rather than an unrelated secondary hue (e.g., rejected the cyan accent and returned to purple tones). Confidence: 0.7
- Prefers short, punchy copy and will ask to trim supporting/hero text down further into a single brief line. Confidence: 0.6
- Prefers an overall dark theme: explicitly rejects light purple ("no quiero morado claro") in favour of dark purple backgrounds that the content and accents stand out against. This extends to individual surfaces: rejects white card/panel backgrounds and wants cards in a dark translucent purple tone that contrasts with the purple page background while staying inside the brand palette. Confidence: 0.7
- Briefly wanted each main section to carry its own dark-purple gradient/glow effect tailored to that area (e.g., magenta for favourites, indigo for tickets, violet for my-events, blue for create/edit) so every screen felt distinct — but reversed this, concluding that differing colours between hero and body "no se ve bien". Confidence: 0.3
- Wants ONE uniform background colour across the entire app — navbar, hero, and every section/body sharing the exact same dark-purple gradient (implemented as a single fixed background layer behind the whole app), so there are no colour "cortes" between regions. Confidence: 0.8
- Even when regions share the same background colour, wants clear visual demarcation between major page areas: a subtle separating line/border at the boundary (e.g., a thin light `border-b` where the hero ends) so the page does not read as a single undifferentiated block ("parece que es de corrido todo"). Confidence: 0.5
- Rejects redundant navigation: asks to remove nav entries that ultimately lead to the same destination (e.g., deleted both "Descubrir" and "Categorías" because they both went to the same page). Confidence: 0.55
- Prefers compact, denser card listings: asks for smaller event cards and tighter grids (more columns per row, smaller image height/padding/text, reduced gaps) rather than large spacious cards. Confidence: 0.55
- Propagates an already-established visual treatment by reference: points at a component whose style they like (e.g., "the same colour you gave the event cards") and asks to apply it to every other surface — auth screens, form panels, list items — expecting the whole app to converge on one consistent look (and re-colouring any adopted design to that shared colour so it contrasts with the rest). Expects the restyle to reach every instance of a surface, including secondary states such as empty-state and error-state panels, and will flag a missed box (often by screenshot) for the agent to catch proactively. Confidence: 0.65
- Batches several distinct change requests into one message, often enumerating them as ordered points ("punto número 1", "punto número 2"), and expects all of them addressed in that same turn. Confidence: 0.55
- Wants images displayed according to their own type/proportion instead of being forced into a fixed cropped box: an image preview must show the whole image respecting its native aspect ratio (e.g., `object-contain` + `max-h`/`max-w`) rather than `object-cover` that cuts off non-landscape images. Confidence: 0.6
- Wants fallback/placeholder imagery to be specific to each item rather than one shared generic fallback: each card that lacks a real image should get filler content tied to what that card itself says (its category/title). Confidence: 0.5
- When raising an existing issue or asking to change current behavior, wants to be guided to exactly where in the code that logic lives (the specific file/component) — not only to have it silently fixed. Confidence: 0.5
- When the agent presents clarifying questions whose options each carry a "recommended" default, tends to reply with a plain go-ahead ("ok ... porfas") instead of choosing option-by-option; expects the agent to pick the recommended/most pragmatic defaults and implement rather than blocking on the questions. Confidence: 0.5
- Expects clear, explicit success/confirmation feedback after a user completes an action (e.g., a "registro completado" confirmation that stays on screen) — an action that silently reverts or leaves the user unsure whether it worked is treated as a bug. Confidence: 0.55
- Wants password fields to include a show/hide ("ojito") toggle so the user can verify what they typed. Confidence: 0.5
